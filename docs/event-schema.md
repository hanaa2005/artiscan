# ساختار داده رویدادها — ArtiScan

نسخه Schema: **۱**

این سند مرجع رسمی ساختار فایل خروجی ArtiScan است. تعریف TypeScript متناظر در
[`src/features/drawing/types/drawing.types.ts`](../src/features/drawing/types/drawing.types.ts)
قرار دارد.

---

## اصل حاکم

> رویدادها داده اصلی هستند. تصویر نهایی یک **خروجی مشتق‌شده** است.

از این اصل سه قانون عملی نتیجه می‌شود که در سراسر کد رعایت شده‌اند:

1. **داده خام هرگز به‌خاطر نمایش تغییر نمی‌کند.** تغییر اندازه پنجره، بزرگ‌نمایی یا هر
   تغییر ظاهری دیگری روی مقادیر ذخیره‌شده اثر ندارد.
2. **هر چیزی که در فایل هست باید برای بازسازی کامل کافی باشد.** اگر چیزی از فایل حذف
   شود و نتوان نقاشی را دقیقاً بازساخت، آن فیلد لازم بوده است.
3. **`strokes` فقط اضافه می‌شود (Append-only).** Undo، Redo و Clear هیچ خطی را حذف
   نمی‌کنند؛ آن‌ها فقط رویدادهایی هستند که **قابل مشاهده بودن** خطوط را تغییر می‌دهند.
   بخش [مدل قابلیت مشاهده](#مدل-قابلیت-مشاهده) این موضوع را کامل توضیح می‌دهد.

## `DrawingSession` — کل جلسه

```jsonc
{
  "schemaVersion": 1,
  "id": "fcaefe88-dbee-4e0f-a174-5b2bd94839f2",
  "createdAt": "2026-08-09T10:10:23.257Z",
  "startedAt": "2026-08-09T10:10:23.257Z",
  "canvas": { "width": 1166, "height": 318, "devicePixelRatio": 1 },
  "strokes": [ /* DrawingStroke[] */ ],
  "actions": [ /* DrawingAction[] */ ]
}
```

| میدان | نوع | توضیح |
|---|---|---|
| `schemaVersion` | `1` | نسخه ساختار فایل. هنگام Import بررسی می‌شود و نسخه ناشناخته رد می‌گردد. |
| `id` | `string` | شناسه یکتای جلسه، تولیدشده با `crypto.randomUUID()`. |
| `createdAt` | `string` | برچسب تقویمی ISO 8601. **یک اندازه‌گیری نیست.** |
| `startedAt` | `string` | زمان شروع جلسه (ISO 8601). |
| `canvas` | `object` | ابعاد بوم در لحظه ساخت خروجی، به‌همراه `devicePixelRatio`. |
| `strokes` | `DrawingStroke[]` | **تمام** خطوط تکمیل‌شده، به ترتیب رسم. Append-only — هرگز چیزی از آن حذف نمی‌شود. |
| `provenance` | `SessionProvenance?` | فقط روی جلساتی که از Schema قدیمی ارتقا یافته‌اند. نبودِ آن یعنی جلسه به‌صورت بومی در نسخه ۲ ضبط شده است. |
| `actions` | `DrawingAction[]` | رویدادهای غیر رسم، به ترتیب وقوع. |

> `canvas` برای بازسازی **لازم نیست** (چون مختصات نرمال‌شده وجود دارد)، اما ثبت می‌شود چون
> برای تفسیر مقادیر خام `x`/`y` و برای تحلیل اثر اندازه صفحه در آینده ضروری است.

## `DrawingStroke` — یک خط

یک حرکت پیوسته از لحظه فشردن تا رها کردن.

```jsonc
{
  "id": "c3a74971-1d7e-46ac-8d50-8fdd3d3a783c",
  "order": 0,
  "tool": "pen",
  "color": "#1f2933",
  "width": 4,
  "startedAtMs": 1461,
  "endedAtMs": 1593.9,
  "hasPressureSamples": false,
  "points": [ /* PointSample[] */ ]
}
```

| میدان | نوع | توضیح |
|---|---|---|
| `id` | `string` | شناسه یکتای خط (`crypto.randomUUID()`). |
| `order` | `number` | ترتیب خط در نقاشی، از صفر. هنگام ساخت خروجی محاسبه می‌شود تا پس از Undo/Redo هم درست بماند. |
| `tool` | `"pen"` \| `"eraser"` | ابزار استفاده‌شده. |
| `color` | `string` | رنگ CSS. برای پاک‌کن ذخیره می‌شود اما در رسم استفاده نمی‌شود. |
| `width` | `number` | ضخامت خط بر حسب پیکسل بوم. |
| `startedAtMs` | `number` | میلی‌ثانیه از شروع جلسه تا اولین نقطه. |
| `endedAtMs` | `number` | میلی‌ثانیه از شروع جلسه تا رها شدن اشاره‌گر. |
| `hasPressureSamples` | `boolean` | آیا حداقل یک نقطه این خط مقدار `pressure` غیر `null` دارد. فقط **وجود** نمونه را ادعا می‌کند، نه تغییر کردن آن. |
| `points` | `PointSample[]` | نمونه‌های نقطه، به ترتیب زمان. |

### پاک‌کن

پاک‌کن **دقیقاً مثل یک خط معمولی** ذخیره می‌شود، فقط با `tool: "eraser"`. از دید ثبت
فرایند، پاک‌کردن هم یک عمل کاربر است و باید در تاریخچه باقی بماند. تفاوت فقط در نمایش
است: هنگام رسم با `globalCompositeOperation: 'destination-out'` کشیده می‌شود.

## `PointSample` — یک نقطه

```jsonc
{
  "sequence": 2,
  "timeMs": 1473,
  "x": 406.33,
  "y": 102.33,
  "normalizedX": 0.34848,
  "normalizedY": 0.3218,
  "pressure": null,
  "tiltX": null,
  "tiltY": null,
  "pointerType": "mouse"
}
```

| میدان | نوع | توضیح |
|---|---|---|
| `sequence` | `number` | شماره ترتیب یکتا در **کل جلسه**. |
| `timeMs` | `number` | میلی‌ثانیه از شروع جلسه، با `performance.now()`، گرد شده به ۰٫۱ میلی‌ثانیه. |
| `x`, `y` | `number` | مختصات خام پیکسلی روی بوم، گرد شده به ۰٫۰۱ پیکسل. |
| `normalizedX`, `normalizedY` | `number` | همان مختصات بین ۰ و ۱، گرد شده به ۵ رقم اعشار. |
| `pressure` | `number \| null` | فشار واقعی قلم بین ۰ و ۱، یا `null`. |
| `tiltX`, `tiltY` | `number \| null` | زاویه قلم بر حسب درجه، یا `null`. |
| `pointerType` | `"mouse" \| "pen" \| "touch" \| "unknown"` | نوع دستگاه ورودی. |

### چرا هم `x` و هم `normalizedX`؟

- `normalizedX/Y` **برای بازسازی** است. نمایش همیشه از روی این مقادیر ضرب در اندازه فعلی
  بوم محاسبه می‌شود، بنابراین نقاشی پس از Resize و روی هر صفحه دیگری یکسان بازسازی
  می‌شود.
- `x`/`y` **برای تحلیل** است. سرعت و شتاب حرکت روی همان صفحه‌ای که رسم انجام شده معنی
  دارد و برای محاسبه‌شان به پیکسل واقعی نیاز است.

### چرا `pressure` برای موس `null` است؟

طبق استاندارد Pointer Events، دستگاهی که فشار را نمی‌سنجد در حالت فشرده مقدار ثابت
**`0.5`** گزارش می‌کند. ثبت این عدد یعنی وارد کردن یک **ثابت ساختگی** به مجموعه داده که
ظاهر اندازه‌گیری دارد اما نیست. بنابراین:

- `pointerType === "pen"` → فشار پذیرفته می‌شود.
- موس، لمس یا نامشخص → `pressure: null`.

همین قانون برای `tiltX`/`tiltY` هم اعمال می‌شود.

### چرا نام `hasPressureSamples` است و نه `hasRealPressure`؟

نام قبلی `hasRealPressure` بود و مستنداتش می‌گفت «فشار واقعی و **متغیر**» — اما کد هرگز
تغییر کردن فشار را بررسی نمی‌کرد؛ فقط چک می‌کرد که حداقل یک نمونه غیر `null` وجود دارد.

این یک اختلاف کوچک به‌نظر می‌رسد ولی برای داده پژوهشی نیست: فیلدی که **بیش از آنچه
اندازه گرفته شده ادعا کند، از نبودِ آن فیلد بدتر است**. تحلیل‌گر هفته‌های بعد به آن اعتماد
می‌کند و نتیجه اشتباه می‌گیرد.

بنابراین نام به اندازه چیزی که کد واقعاً آزمایش می‌کند **باریک** شد:

> `hasPressureSamples: true` یعنی «این خط نمونه فشار دارد». نه بیشتر.

اینکه فشار **تغییر کرده یا نه** سوالی برای مرحله استخراج ویژگی است و از روی
`points[].pressure` قابل پاسخ است — تمام مقادیر خام حفظ شده‌اند.

## `DrawingAction` — رویدادهای غیر رسم

```jsonc
{ "sequence": 27, "timeMs": 1964.2, "type": "undo", "payload": { "strokeId": "c3a749..." } }
```

| میدان | نوع | توضیح |
|---|---|---|
| `sequence` | `number` | شماره ترتیب یکتا در کل جلسه (شمارنده مشترک با نقاط). |
| `timeMs` | `number` | میلی‌ثانیه از شروع جلسه. |
| `type` | enum | نوع رویداد (جدول زیر). |
| `payload` | `object?` | اطلاعات تکمیلی؛ اختیاری. |

| `type` | `payload` | معنی |
|---|---|---|
| `undo` | `{ strokeId }` | آخرین خط قابل‌مشاهده **پنهان** شد. |
| `redo` | `{ strokeId }` | خط پنهان‌شده دوباره **نمایش** داده شد. |
| `clear` | `{ affectedStrokeIds: string[] }` | همه خطوط قابل‌مشاهده در آن لحظه **پنهان** شدند. |
| `tool_change` | `{ from, to }` | تغییر ابزار بین قلم و پاک‌کن. |
| `color_change` | `{ from, to }` | تغییر رنگ. |
| `width_change` | `{ from, to }` | تغییر ضخامت. |

## نسخه‌بندی Schema و سیاست سازگاری

### چرا نسخه ۲؟

نسخه ۱ و نسخه ۲ **دقیقاً همان نام فیلدها** را دارند اما **تضمین‌های متفاوتی** می‌دهند.
این خطرناک‌ترین نوع تفاوت است، چون فایل سالم به نظر می‌رسد ولی معنایش عوض شده:

| | Schema 1 | Schema 2 |
|---|---|---|
| `strokes` | مخرب — Undo و Clear خطوط را حذف می‌کردند | Append-only — هرگز چیزی حذف نمی‌شود |
| `clear` payload | `{ removedStrokeCount }` — فقط تعداد | `{ affectedStrokeIds }` — شناسه دقیق، **الزامی** |
| Undo | خط را از فایل حذف می‌کرد | فقط پنهان می‌کند |
| فیلد فشار | `hasRealPressure` | `hasPressureSamples` |
| تاریخچه | ناقص پس از هر Clear | کامل |

اگر یک فایل نسخه ۱ را به‌عنوان نسخه ۲ بخوانیم، سامانه بی‌سروصدا ادعا می‌کند تاریخچه
کامل است — در حالی که نیست. به همین دلیل شماره نسخه **باید** تغییر می‌کرد.

### سیاست خواندن

| نسخه فایل | رفتار |
|---|---|
| ۱ | **خوانده می‌شود** و ارتقا می‌یابد. مسیر ارتقا کاملاً جدا است: [`services/legacySchemaV1.ts`](../src/features/drawing/services/legacySchemaV1.ts) |
| ۲ | خوانده می‌شود با اعتبارسنجی کامل |
| ۳ و بالاتر | **رد می‌شود** با پیام فارسی — این نسخه نمی‌داند آن فایل چه تضمین‌هایی می‌دهد |

خروجی همیشه نسخه ۲ است.

### قانونی که هرگز نقض نمی‌شود

**خطوطی که Clear مخرب نسخه ۱ از بین برده، بازیابی‌شدنی نیستند و ساخته نمی‌شوند.**

ماژول ارتقا هرگز خطی اختراع نمی‌کند، هرگز از روی `removedStrokeCount` فهرست شناسه
نمی‌سازد و هرگز حدس نمی‌زند چه چیزی پاک شده است. فقط ظرف را ارتقا می‌دهد، هر بایت
باقی‌مانده را حفظ می‌کند و نتیجه را **صادقانه به‌عنوان تاریخچه ناقص برچسب می‌زند**.

### علامت‌گذاری تاریخچه ناقص

```jsonc
"provenance": {
  "importedFromSchemaVersion": 1,
  "historyComplete": false,
  "note": "...این جلسه از فایل نسخه ۱ خوانده شده و تاریخچه آن ناقص است"
}
```

`historyComplete: false` وقتی ست می‌شود که:
- فایل نسخه ۱ حداقل یک رویداد `clear` با `removedStrokeCount > 0` داشته باشد، **یا**
- یک رویداد `undo`/`redo` به خطی اشاره کند که در فایل نیست (نشانه دیگرِ مدل مخرب).

این برچسب **در هر Export مجدد هم باقی می‌ماند**. یعنی نمی‌توان با یک بار Import و
Export، یک تاریخچه ناقص را به فایل نسخه ۲ تمیز تبدیل کرد. «این ضبط سوراخ دارد» یک
ویژگی دائمی داده است، نه یک هشدار یک‌بارمصرف.

### ترجمه رویداد `clear` نسخه ۱

```jsonc
// نسخه ۱ (ورودی)
{ "type": "clear", "payload": { "removedStrokeCount": 4 } }

// نسخه ۲ (خروجی ارتقا)
{ "type": "clear", "payload": {
    "affectedStrokeIds": [],          // هیچ خط باقی‌مانده‌ای را پنهان نمی‌کند
    "legacyDestructiveClear": true,   // نشانه اینکه این Clear مخرب بوده
    "removedStrokeCount": 4           // تنها ردِ باقی‌مانده از خطوط ازدست‌رفته
} }
```

فهرست شناسه‌ها **خالی** است و این ترجمه درست است: آن Clear هیچ‌کدام از خطوطی که هنوز
در فایل هستند را پاک نکرده بود. `removedStrokeCount` حذف نمی‌شود چون تنها شاهد باقی‌مانده
از داده ازدست‌رفته است — «۴ خط اینجا نیست» خودش یک اطلاعات واقعی است.

## قرارداد ترتیب زمانی

سه قانون که تمام تحلیل‌های هفته‌های بعد به آن‌ها تکیه می‌کنند:

### ۱. `timeMs` صعودی و غیرنزولی است (Monotonic Non-Decreasing)

هیچ رویدادی نمی‌تواند `timeMs` کوچک‌تر از رویداد قبلی خود داشته باشد. این تضمین از
`performance.now()` می‌آید که ساعتی یکنواخت است و هرگز عقب نمی‌رود.

اما **مساوی بودن مجاز است**: زمان با دقت ۰٫۱ میلی‌ثانیه گرد می‌شود و یک دیجیتایزر سریع
می‌تواند چند نمونه را داخل همان یک‌دهم میلی‌ثانیه تحویل دهد.

### ۲. `sequence` مرجع نهایی ترتیب است

وقتی دو رویداد `timeMs` یکسان دارند، **`sequence` تصمیم می‌گیرد**. این عدد از یک شمارنده
واحد می‌آید که اکیداً صعودی است و هرگز تکرار نمی‌شود.

هر کدی که به ترتیب زمانی نیاز دارد باید با
[`compareTimeline()`](../src/features/drawing/utils/timing.ts) مرتب کند، نه با `timeMs`
تنها.

این تضمین در **کل خط زمانی ادغام‌شده** اعمال می‌شود، نه فقط داخل هر آرایه — بخش
[لایه ۲ب](#لایه-۲ب--چرا-بررسی-هر-آرایه-بهتنهایی-کافی-نیست) را ببینید.

### ۳. برای محاسبات سرعت، `dt <= 0` باید امن مدیریت شود

تمام ویژگی‌های سرعت و شتاب در هفته‌های بعد بر این فاصله زمانی تقسیم می‌کنند. دو نقطه
می‌توانند به‌طور قانونی `timeMs` یکسان داشته باشند و تقسیم بر صفر مقدار `Infinity`
می‌دهد — عددی که بی‌سروصدا هر میانگین، بیشینه یا نمودار را خراب می‌کند.

به همین دلیل [`safeDeltaMs()`](../src/features/drawing/utils/timing.ts) در چنین حالتی
`null` برمی‌گرداند و محاسبه‌کننده را **مجبور** می‌کند تصمیم بگیرد با یک بازه
اندازه‌گیری‌نشدنی چه کند:

```ts
const delta = safeDeltaMs(previousPoint, currentPoint)
const speed = delta === null ? null : distance / delta   // هرگز Infinity
```

## مدل قابلیت مشاهده

این مهم‌ترین بخش این سند است.

### مسئله

اگر Clear خطوط را از `strokes` **حذف** کند، فایل خروجی فقط این را نگه می‌دارد که «۴ خط
پاک شد» — و شناسه، نقاط، زمان‌بندی و ابزار آن ۴ خط برای همیشه از بین می‌رود. برای یک
سامانه‌ای که هدفش ثبت فرایند است، این یعنی از دست دادن دقیقاً همان چیزی که باید ثبت
می‌شد. کاربری که چیزی می‌کشد و بعد پاک می‌کند، یک **رفتار معنادار** انجام داده است.

### راه‌حل

`strokes` فقط اضافه می‌شود. Undo، Redo و Clear رویدادهایی هستند که **قابل مشاهده بودن**
را تغییر می‌دهند، نه وجود داشتن را:

- `strokes` → داده پژوهشی (کل تاریخچه)
- `strokes` + `actions` → آنچه روی بوم دیده می‌شود

### الگوریتم بازپخش

پیاده‌سازی در [`utils/strokeVisibility.ts`](../src/features/drawing/utils/strokeVisibility.ts):

```
visible ← مجموعه شناسه تمام خطوط
برای هر action به ترتیب:
    undo   → visible.delete(payload.strokeId)
    redo   → visible.add(payload.strokeId)
    clear  → برای هر id در payload.affectedStrokeIds: visible.delete(id)

نتیجه: strokes.filter(s => visible.has(s.id))   ← به ترتیب اصلی رسم
```

### چرا ارجاع با **شناسه** و نه با تعداد یا موقعیت؟

این تصمیم کلیدی است و باعث می‌شود بازپخش **مستقل از ترتیب** و ایمن باشد:

یک رویداد `clear` فقط می‌تواند شناسه‌هایی را نام ببرد که **در آن لحظه وجود داشتند**.
بنابراین خطی که **بعد از** Clear کشیده شده، ممکن نیست در آن فهرست باشد و به‌طور خودکار
دست‌نخورده می‌ماند. به همین دلیل نیازی به ادغام دو خط زمانی یا محاسبه روی `sequence`
نیست — یک حلقه ساده کافی است.

با «تعداد» (`removedStrokeCount`) چنین چیزی ممکن نبود: عدد ۴ نمی‌گوید **کدام** ۴ خط.

### ترتیب رسم پس از Redo

خطوط همیشه به **ترتیب اصلی ایجاد** رسم می‌شوند، نه به ترتیبی که Redo آن‌ها را برگردانده
است. این برای پاک‌کن حیاتی است: یک خط پاک‌کن باید همیشه دقیقاً روی همان جوهری اعمال شود
که قبل از آن وجود داشته است.

### مثال

```jsonc
{
  "strokes": [
    { "id": "a", "order": 0, /* ... نقاط و زمان‌بندی کامل ... */ },
    { "id": "b", "order": 1, /* ... */ },
    { "id": "c", "order": 2, /* ... */ },
    { "id": "d", "order": 3, /* ... */ },
    { "id": "e", "order": 4, /* ... */ }
  ],
  "actions": [
    { "sequence": 60, "timeMs": 8100, "type": "clear",
      "payload": { "affectedStrokeIds": ["a", "b", "c", "d"] } }
  ]
}
```

- **داده پژوهشی:** هر ۵ خط، با تمام نقاط و زمان‌بندی.
- **بوم قابل مشاهده:** فقط خط `e` (که بعد از Clear کشیده شده).

### Clear در رابط کاربری

Clear همچنان در رابط کاربری **غیرقابل بازگشت** است (Undo آن را برنمی‌گرداند) و پیام تایید
دارد. اما در داده پژوهشی **کاملاً غیرمخرب** است.

### سازگاری با فایل‌های قدیمی

فایل‌های قدیمی که رویداد `clear` با `{ removedStrokeCount }` دارند بدون خطا خوانده
می‌شوند: نبود `affectedStrokeIds` به معنای «هیچ خطی پنهان نشود» تفسیر می‌شود. چون در آن
فایل‌ها خطوط پاک‌شده اصلاً ذخیره نشده بودند، نتیجه نمایشی همچنان درست است.

---

### بازیابی Redo از روی تاریخچه

Redo فقط یک وضعیت رابط کاربری نیست — **در داده ثبت‌شده وجود دارد**. اگر کاربر خطی را
Undo کند و جلسه ذخیره شود، هم خط در `strokes` هست و هم رویداد `undo` در `actions`. پس
«چیزی برای Redo وجود دارد» یک واقعیت ضبط‌شده است.

به همین دلیل `loadSession` پشته Redo را **بازسازی می‌کند**، نه خالی. همان تابع
`replayHistory()` که تعیین می‌کند چه چیزی دیده شود، پشته Redo را هم می‌سازد، بنابراین
وضعیت بازیابی‌شده نمی‌تواند از تاریخچه ضبط‌شده جدا بیفتد.

قوانین بازپخش دقیقاً همان قوانین ویرایشگر زنده است:

| رویداد در Timeline | اثر روی دیده‌شدن | اثر روی پشته Redo |
|---|---|---|
| رسم خط جدید | نمایش | **خالی می‌شود** |
| `undo` | پنهان | خط به پشته اضافه می‌شود |
| `redo` | نمایش | خط از پشته برداشته می‌شود |
| `clear` | پنهان‌کردن خطوط نام‌برده | **خالی می‌شود** |

توجه: برای پاسخ به «آیا این خط قبل از آن Undo کشیده شده یا بعد از آن؟» باید خطوط و
رویدادها روی **یک Timeline واحد** ادغام شوند — و این دقیقاً کاری است که `sequence`
ممکن می‌کند.

### اعتبارسنجی سه‌لایه هنگام Import

| لایه | چه چیزی بررسی می‌شود | روی کدام نسخه |
|---|---|---|
| **۱. شکل** | نوع هر فیلد، بازه‌ها (`normalized` بین ۰ و ۱، ضخامت مثبت، ...) | هر دو |
| **۲. ساختار** | شناسه یکتا، `sequence` یکتا و صعودی، `order` یک جایگشت تمیز ۰..n-1، `startedAtMs <= endedAtMs` | هر دو |
| **۲ب. خط زمانی ادغام‌شده** | با صعودی شدن `sequence`، هیچ‌جا `timeMs` کاهش نیابد — در **مقایسه نقاط و رویدادها با یکدیگر** | هر دو |
| **۳. ارجاع** | `undo`/`redo` به خط موجود اشاره کند؛ `clear` فهرست `affectedStrokeIds` داشته باشد و به خطوط موجود اشاره کند | **فقط نسخه ۲** |
| **۴. معنای زمانی** | ماشین حالت: هر عمل با وضعیت **همان لحظه** سنجیده شود | **فقط نسخه ۲** |

لایه‌های ۳ و ۴ عمداً روی نسخه ۱ اجرا **نمی‌شوند**. در آن مدل، یک `undo` که به خط
حذف‌شده اشاره می‌کند نتیجه طبیعی سیستم بود، نه یک نقص — اعمال قانون سخت‌گیرانه،
فایل‌های کاملاً معتبر قدیمی را رد می‌کرد.

#### لایه ۲ب — چرا بررسی هر آرایه به‌تنهایی کافی نیست

نقاط و رویدادها در دو آرایه جدا ذخیره می‌شوند اما در **یک ترتیب درهم‌تنیده** رخ داده‌اند.
بررسی جداگانه هر آرایه تقریباً هیچ چیز اثبات نمی‌کند: هر دو می‌توانند کاملاً صعودی باشند
در حالی که یک رویداد ادعا می‌کند قبل از نقطه‌ای رخ داده که در `sequence` جلوتر از آن است.

```jsonc
// هر آرایه به‌تنهایی سالم است، ولی ادغام‌شده متناقض است:
"strokes": [{ "points": [ {"sequence": 1, "timeMs": 100},
                          {"sequence": 2, "timeMs": 200},
                          {"sequence": 3, "timeMs": 300} ] }],
"actions": [ { "sequence": 4, "timeMs": 50 } ]   // ← رد می‌شود
```

مساوی بودن `timeMs` همچنان معتبر است؛ `sequence` مرجع نهایی است.

#### لایه ۴ — معنای زمانی (ماشین حالت)

لایه ۳ می‌پرسد «آیا این شناسه **جایی** در فایل هست؟» — سوالی درباره کل فایل، بدون هیچ
مفهومی از زمان. بنابراین یک `undo` از خطی که **هنوز کشیده نشده** یا یک `redo` بدون
`undo` قبلی را می‌پذیرد. چنین فایلی جلسه‌ای را توصیف می‌کند که **ممکن نیست رخ داده باشد**:
بازپخشش بومی می‌سازد که کاربر هرگز ندیده، و زمان‌ها و شمارش‌های آن ساختگی‌اند.

پس لایه ۴ خطوط و رویدادها را به ترتیب `sequence` با هم می‌پیماید و در هر گام سه چیز را
نگه می‌دارد: مجموعه خطوط **ایجادشده**، مجموعه خطوط **قابل‌مشاهده**، و **پشته Redo**.

قواعد رد کردن:

| وضعیت | چرا نامعتبر است |
|---|---|
| `undo`/`redo` به خطی که `sequence` اولین نقطه‌اش **بعد از** خودِ عمل است | ارجاع به آینده |
| `undo` از خطی که در آن لحظه **قابل مشاهده نبود** | نمی‌توان چیزی را که روی بوم نیست برداشت |
| `redo` بدون یک `undo` متناظر (پشته خالی) | چیزی برای بازگرداندن وجود نداشت |
| `redo` از شناسه‌ای که **بالای پشته نیست** | پشته LIFO است؛ ویرایشگر هرگز چنین چیزی تولید نمی‌کند |
| `clear` به خطی که هنوز ایجاد نشده | ارجاع به آینده |
| `clear` با شناسه **تکراری** | یک خط دو بار پاک نمی‌شود |
| `clear` به خطی که در آن لحظه قابل مشاهده نبود | آن خط از قبل پنهان بوده |

دو رویداد هم پشته Redo را **خالی** می‌کنند: رسم یک خط جدید، و `clear`.

خطاهایی که لایه ۲ می‌گیرد برنامه را Crash نمی‌کنند؛ آن‌ها **تحلیل را خراب می‌کنند**:
شناسه تکراری هر جست‌وجوی مبتنی بر شناسه را مبهم می‌کند، `sequence` تکراری Timeline ادغام‌شده
را نابود می‌کند، و `order` تکراری «سومین خطی که کشیده شد» را بی‌معنا می‌کند. گرفتن آن‌ها
در لحظه Import تنها فرصت ارزان است — بعد از آن، داده خراب از داده سالم قابل تشخیص نیست.

### چرا شمارنده `sequence` بین نقاط و رویدادها مشترک است؟

چون با این کار، مرتب‌کردن همه نقاط و رویدادها بر اساس `sequence` **دقیقاً** ترتیب واقعی
اتفاقات را بازتولید می‌کند: «کاربر ۲۰ نقطه کشید، بعد Undo زد، بعد رنگ را عوض کرد، بعد ۱۵
نقطه دیگر کشید». با دو شمارنده جدا این ترتیب مطلق از دست می‌رفت.

## قوانین اعتبارسنجی هنگام Import

فایل ورودی **ورودی غیرقابل‌اعتماد** در نظر گرفته می‌شود. هیچ خطایی نباید برنامه را
متوقف کند؛ هر شکست یک پیام فارسی برمی‌گرداند.

ترتیب بررسی‌ها:

1. مقدار یک شیء باشد (نه آرایه، نه `null`، نه عدد یا رشته).
2. `schemaVersion` وجود داشته و برابر `1` باشد.
3. `id`، `createdAt` و `startedAt` رشته‌های غیرخالی باشند.
4. `canvas` وجود داشته و `width`/`height` اعداد مثبت باشند.
5. `strokes` و `actions` آرایه باشند.
6. برای هر خط: `id`، `order`، `tool` معتبر، `color`، `width > 0`، زمان‌های عددی، `points` آرایه.
7. برای هر نقطه: اعداد متناهی، `timeMs >= 0`، `normalizedX/Y` بین ۰ و ۱، `pointerType` معتبر.
8. برای هر رویداد: `sequence` و `timeMs` عددی، `type` از فهرست مجاز.

سپس لایه‌های **ساختار** و **ارجاع** اجرا می‌شوند — جدول کامل در بخش
[اعتبارسنجی سه‌لایه](#اعتبارسنجی-سه‌لایه-هنگام-import).

مقدار `hasPressureSamples` اگر در فایل نباشد به `false` مقداردهی می‌شود — این تنها موردی
است که به‌جای رد کردن، مقدار پیش‌فرض گذاشته می‌شود. (در فایل نسخه ۱ این فیلد
`hasRealPressure` نام دارد و هنگام ارتقا نگاشت می‌شود.)

## تغییر Schema در آینده

اگر ساختار به‌شکل ناسازگار تغییر کند:

1. `CURRENT_SCHEMA_VERSION` در `drawing.types.ts` افزایش یابد.
2. در `drawingValidator.ts` یک مسیر مهاجرت برای نسخه قدیمی اضافه شود.
3. این سند به‌روزرسانی شود.

تا زمانی که فقط **فیلد اختیاری جدید** اضافه شود، افزایش نسخه لازم نیست.
