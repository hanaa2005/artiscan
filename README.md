# ArtiScan — آزمایشگاه ثبت فرایند نقاشی

> ⚠️ **این نسخه یک نمونه اولیه پژوهشی است.** تمام داده‌های تولیدشده آزمایشی هستند و
> سامانه **هیچ تحلیل، تفسیر یا کاربرد تشخیصی روان‌شناختی ندارد**. جزئیات بیشتر در بخش
> [محدودیت‌ها و ملاحظات علمی](#محدودیتها-و-ملاحظات-علمی).

ArtiScan یک سامانه تحت وب برای ثبت **فرایند** نقاشی است، نه فقط تصویر نهایی آن.

نرم‌افزارهای معمول نقاشی در پایان یک فایل تصویری تحویل می‌دهند؛ در آن فایل هیچ نشانی از
اینکه کاربر از کجا شروع کرد، کجا مکث کرد، چند بار پاک کرد و با چه سرعتی خط کشید باقی
نمی‌ماند. ArtiScan برعکس عمل می‌کند: **رویدادها داده اصلی سامانه هستند** و تصویر نهایی صرفاً
یکی از خروجی‌هایی است که از روی همان رویدادها ساخته می‌شود.

این مخزن، خروجی **هفته اول** پروژه است: هسته فرانت‌اند و سیستم ثبت رویداد.

## نصب و اجرا

پیش‌نیاز: **Node.js نسخه ۲۰ یا بالاتر** (توسعه با Node 24 انجام شده است).

```bash
npm install      # نصب وابستگی‌ها
npm run dev      # اجرای محیط توسعه روی http://localhost:5173
```

دستورهای دیگر:

```bash
npm run test         # اجرای تست‌ها (Vitest)
npm run test:watch   # اجرای تست‌ها در حالت watch
npm run typecheck    # بررسی نوع‌ها بدون ساخت خروجی
npm run lint         # بررسی کیفیت کد (oxlint)
npm run build        # ساخت نسخه production در پوشه dist
npm run preview      # پیش‌نمایش خروجی build
```

## اجرای یک آزمون و گرفتن خروجی

برنامه دو حالت دارد که از بالای صفحه انتخاب می‌شوند:

| حالت | کاربرد |
|---|---|
| **اجرای آزمون** | جریان کامل آزمون: انتخاب تکلیف، دستورالعمل، شمارش معکوس، رسم زمان‌دار، استخراج ویژگی و خروجی نتیجه |
| **رسم آزاد** | آزمایشگاه هفته اول، بدون تغییر: رسم، Undo/Redo، ورود و خروجی JSON، خروجی PNG |

### مراحل یک آزمون

۱. **انتخاب تکلیف** — یکی از ۱۰ تکلیف را بزنید یا «انتخاب تصادفی» را انتخاب کنید.
۲. **دستورالعمل** — متن تکلیف و زمان پیشنهادی را بخوانید، سپس «آماده‌ام، شروع کن».
۳. **شمارش معکوس** — ۳ ثانیه. از این لحظه **تکلیف قفل می‌شود** و دیگر قابل تغییر نیست.
۴. **رسم** — بوم فعال می‌شود و زمان سپری‌شده نمایش داده می‌شود. تمام ابزارهای هفته اول
   (قلم، پاک‌کن، رنگ، ضخامت، Undo، Redo، Clear) در دسترس‌اند.
۵. **پایان** — «پایان و ثبت نتیجه» را بزنید. جلسه فریز می‌شود و نتیجه ساخته می‌شود.
۶. **خروجی** — «خروجی JSON نتیجه آزمون» فایلی با این نام می‌سازد:
   `artiscan-trial-<تکلیف>-<شناسه>-<تاریخ>.json`

### داخل فایل نتیجه چیست؟

```jsonc
{
  "resultSchemaVersion": 2,          // نسخه پوشش نتیجه
  "trial":     { /* زمان‌بندی و وضعیت آزمون */ },
  "task":      { /* تکلیفی که خواسته شده بود */ },
  "session":   { "schemaVersion": 2, /* داده خام، بدون تغییر */ },
  "features":  { /* ویژگی‌های محاسبه‌شده: خام و داخل بوم */ },
  "timePolicy":{ /* مقایسه مدت واقعی با زمان پیشنهادی */ }
}
```

`resultSchemaVersion` در بازبینی اصلاحی به **۲** رسید، چون قرارداد `features` تغییر کرد:
هندسه **خام** از هندسه **داخل بوم** جدا شد و `timePolicy` اضافه شد. `session.schemaVersion`
همچنان **۲** است و دست نخورده — بالا بردن آن به‌دروغ می‌گفت خودِ ضبط‌ها نیاز به مهاجرت
دارند. فایل‌های نسخه ۱ همچنان خوانده می‌شوند و ویژگی‌هایشان بازمحاسبه می‌شود.

> **هیچ فیلد مربوط به آزمون داخل `session` اضافه نشده است.** جلسه نقاشی همان چیزی است که
> هفته اول تثبیت شد. جزئیات کامل در [`docs/trial-schema.md`](docs/trial-schema.md).

### هنگام وارد کردن دوباره فایل چه می‌شود؟

ویژگی‌های ذخیره‌شده **دور ریخته و از روی `session` بازمحاسبه** می‌شوند. دلیلش در بخش
[سیاست ویژگی‌ها](docs/trial-schema.md#سیاست-ویژگیها-هنگام-import-بازمحاسبه-نه-اعتماد)
توضیح داده شده: ویژگی‌ها یک Cache هستند، نه داده.

### جریان داده به زبان ساده

```
حرکت قلم
   │
   ▼
DrawingCanvas  ── هندسه DOM: تبدیل مختصات صفحه به مختصات بوم
   │
   ▼
useDrawingSession  ── ثبت نقطه در Event Log (بدون render)
   │
   ├──► رها شدن قلم ──► Stroke کامل وارد State می‌شود ──► یک بار render
   │                                                        │
   │                                                        ▼
   │                                          ذخیره خودکار در IndexedDB
   │
   └──► buildSession() ──► DrawingSession ──► JSON / PNG / آمار
```

نکته کلیدی: **بوم چیزی ثبت نمی‌کند و هوک چیزی نمی‌کشد.** بوم فقط می‌داند مختصات کجاست،
هوک فقط می‌داند چه اتفاقی افتاده است.

### جریان آزمون (هفته دوم)

```
useDrawingTrial            useDrawingSession
   │ (کی؟)                     │ (چه چیزی؟)
   ├─ انتخاب تکلیف              │
   ├─ دستورالعمل                │
   ├─ شمارش معکوس               │
   ├─ شروع رسم ──────────────►  startNewSession()
   │                            ├─ ثبت خطوط
   ├─ پایان                     │
   ▼                            ▼
DrawingTrial              DrawingSession (خام)
   └──────────┬───────────────┘
              ▼
      buildTrialResult()
              │
              ├──► extractDrawingFeatures(session)  ← تابع خالص
              ▼
      DrawingTrialResult ──► JSON
```

همان تفکیک، یک لایه بالاتر: **ماشین حالت نمی‌داند چه کشیده شده و ضبط‌کننده نمی‌داند
آزمونی در جریان است.**

## مدل داده

شرح کامل و میدان‌به‌میدان در [`docs/event-schema.md`](docs/event-schema.md) آمده است. خلاصه:

```ts
DrawingSession          // کل یک جلسه
├── schemaVersion: 2    // نسخه ساختار فایل (نسخه ۱ خوانده و ارتقا می‌شود)
├── id, createdAt, startedAt
├── canvas { width, height, devicePixelRatio }
├── strokes: DrawingStroke[]     // تمام خطوط، به ترتیب رسم — Append-only
│   └── points: PointSample[]    // نقاط هر خط، به ترتیب زمان
└── actions: DrawingAction[]     // Undo / Redo / Clear / تغییر ابزار و رنگ و ضخامت
```

> **`strokes` هرگز کوچک نمی‌شود.** Undo، Redo و Clear خطوط را حذف نمی‌کنند؛ فقط رویدادهایی
> ثبت می‌کنند که تعیین می‌کند کدام خط دیده شود. بخش
> [Clear غیرمخرب](#clear-چگونه-غیرمخرب-است) را ببینید.

هر `PointSample` شامل این موارد است:

| میدان | معنی |
|---|---|
| `sequence` | شماره ترتیب یکتا در کل جلسه (نقاط و رویدادها یک شمارنده مشترک دارند) |
| `timeMs` | میلی‌ثانیه از شروع جلسه، با `performance.now()` |
| `x`, `y` | مختصات خام پیکسلی روی بوم |
| `normalizedX/Y` | همان مختصات، نرمال‌شده بین ۰ و ۱ |
| `pressure` | فشار واقعی قلم، یا `null` |
| `tiltX`, `tiltY` | زاویه قلم، یا `null` |
| `pointerType` | `mouse` \| `pen` \| `touch` \| `unknown` |

## تصمیم‌های فنی کلیدی

این بخش برای دفاع پروژه نوشته شده است — هر تصمیم یک دلیل مشخص دارد.

### ۱. چرا `performance.now()` و نه `Date.now()`؟

`Date.now()` ساعت دیواری سیستم را می‌خواند و می‌تواند به عقب یا جلو **بپرد** (همگام‌سازی
NTP، تغییر ساعت توسط کاربر، ساعت تابستانی). وقتی خودِ فاصله زمانی بین دو نقطه، همان
اندازه‌گیری موردنظر ماست، یک پرش ساعت داده را نامعتبر می‌کند.

`performance.now()` یک ساعت **یکنواخت** (monotonic) با دقت بالاست که فقط رو به جلو حرکت
می‌کند. در کل پروژه `Date.now()` فقط در یک جا استفاده می‌شود: ساخت برچسب تقویمی
`createdAt` که یک اندازه‌گیری نیست.

### ۲. چرا مختصات نرمال‌شده هم ذخیره می‌شود؟

بوم Responsive است و اندازه‌اش با تغییر پنجره عوض می‌شود. مختصات پیکسلی به‌تنهایی بعداً
بی‌معنی است. بنابراین نمایش **همیشه** از روی `normalized × اندازه فعلی` محاسبه می‌شود.
نتیجه: نقاشی بعد از Resize خراب نمی‌شود و فایل واردشده روی هر اندازه صفحه‌ای یکسان
بازسازی می‌شود.

### ۳. چرا فشار موس `null` ذخیره می‌شود؟

طبق استاندارد Pointer Events، دستگاهی که فشار را نمی‌سنجد باید مقدار ثابت **`0.5`**
گزارش کند. ذخیره کردن این عدد به‌عنوان «فشار»، مجموعه داده پژوهشی را با یک ثابت پر
می‌کند که *شبیه* اندازه‌گیری است اما نیست — دقیقاً همان نوع خطایی که تحلیل بعدی را
بی‌اعتبار می‌کند. پس فشار فقط از قلم واقعی (`pointerType === 'pen'`) پذیرفته می‌شود.

### ۴. چرا داده Stroke جاری در Ref است و نه State؟

یک اشاره‌گر می‌تواند بیش از ۱۲۰ رویداد در ثانیه تولید کند و با `getCoalescedEvents()` هر
رویداد چند نمونه دارد. `setState` روی هر نمونه یعنی صدها render در ثانیه و افت شدید
فریم. بنابراین خط در حال رسم داخل یک Ref انباشته می‌شود و **مستقیماً** روی Konva کشیده
می‌شود؛ فقط هنگام رها شدن اشاره‌گر یک `setState` انجام می‌شود.

### ۵. چرا Pointer Capture؟

بدون آن، اگر اشاره‌گر هنگام رسم از بوم خارج شود مرورگر رویدادها را به عنصر دیگری
می‌فرستد و خط ناقص قطع می‌شود. `setPointerCapture()` تضمین می‌کند تمام رویدادهای آن
اشاره‌گر تا لحظه رها شدن به بوم برسند.

### ۶. چرا `getCoalescedEvents()`؟

نمایشگر ۶۰ هرتزی در هر فریم فقط یک `pointermove` تحویل می‌دهد، اما یک دیجیتایزر ۲۴۰
هرتزی در همان مدت چند نمونه واقعی تولید کرده است. این تابع نمونه‌های ادغام‌شده را
برمی‌گرداند — تفاوت بین یک ثبت خشن و یک ثبت دقیق از فرایند رسم. برای مرورگرهای فاقد این
قابلیت، Fallback به خود رویداد وجود دارد.

### ۷. پاک‌کن چگونه کار می‌کند؟

پاک‌کن با `globalCompositeOperation: 'destination-out'` رسم می‌شود: به‌جای رنگ‌زدن،
پیکسل‌های موجود را حذف می‌کند. اما در **داده خام** دقیقاً مثل یک Stroke معمولی با
`tool: "eraser"` ذخیره می‌شود، چون از دید ثبت فرایند، پاک‌کردن هم یک عمل کاربر است.

به همین دلیل خروجی PNG روی یک بوم سفید ترکیب می‌شود؛ در غیر این صورت نواحی پاک‌شده در
فایل PNG **شفاف** می‌ماندند و در اکثر نمایشگرها سیاه دیده می‌شدند.

### ۸. Clear چگونه غیرمخرب است؟

اگر Clear خطوط را واقعاً حذف کند، فایل خروجی فقط نگه می‌دارد که «۴ خط پاک شد» و شناسه،
نقاط، زمان‌بندی و ابزار آن‌ها برای همیشه از بین می‌رود. برای سامانه‌ای که کل هدفش ثبت
فرایند است، این یعنی از دست دادن دقیقاً همان چیزی که باید ثبت می‌شد — کاربری که چیزی
می‌کشد و بعد پاکش می‌کند، یک رفتار معنادار انجام داده است.

بنابراین `strokes` **فقط اضافه می‌شود** و Undo/Redo/Clear رویدادهایی هستند که *قابل
مشاهده بودن* را تغییر می‌دهند:

```
strokes                    ← داده پژوهشی (کل تاریخچه)
strokes + actions          ← آنچه روی بوم دیده می‌شود
```

رویداد Clear شناسه دقیق خطوطی را که پنهان کرده ثبت می‌کند
(`{ affectedStrokeIds: [...] }`). ارجاع با **شناسه** — نه با تعداد و نه با موقعیت — باعث
می‌شود بازپخش مستقل از ترتیب باشد: یک Clear فقط می‌تواند شناسه‌هایی را نام ببرد که در آن
لحظه وجود داشتند، پس خطی که **بعد از** آن کشیده شده به‌طور خودکار دست‌نخورده می‌ماند.

Clear در رابط کاربری همچنان غیرقابل بازگشت است و پیام تایید دارد؛ اما در داده پژوهشی
هیچ چیزی را نابود نمی‌کند. جزئیات کامل در
[`docs/event-schema.md`](docs/event-schema.md#مدل-قابلیت-مشاهده).

### ۹. سازگاری Schema نسخه ۱ و ۲

نسخه ۱ و ۲ همان نام فیلدها را دارند اما تضمین‌های متفاوتی می‌دهند — و این خطرناک‌ترین
نوع تفاوت است، چون فایل سالم به‌نظر می‌رسد ولی معنایش عوض شده:

| | نسخه ۱ | نسخه ۲ |
|---|---|---|
| `strokes` | مخرب (Undo و Clear حذف می‌کردند) | Append-only |
| `clear` | `{ removedStrokeCount }` | `{ affectedStrokeIds }` — الزامی |
| فیلد فشار | `hasRealPressure` | `hasPressureSamples` |

**سیاست:** فایل نسخه ۱ خوانده و ارتقا می‌شود (مسیر جدا در `legacySchemaV1.ts`)، نسخه ۲
مستقیم خوانده می‌شود، نسخه ۳ و بالاتر رد می‌شود. خروجی همیشه نسخه ۲ است.

**قانونی که هرگز نقض نمی‌شود:** خطوطی که Clear مخرب نسخه ۱ از بین برده **ساخته
نمی‌شوند**. آن جلسه با `provenance.historyComplete: false` برچسب می‌خورد و این برچسب در
هر Export مجدد هم باقی می‌ماند — نمی‌توان یک تاریخچه ناقص را با Import/Export به فایل
تمیز تبدیل کرد.

### ۱۰. چرا `hasPressureSamples` و نه `hasRealPressure`؟

نام قبلی ادعای «فشار واقعی و متغیر» می‌کرد، اما کد فقط وجود یک نمونه غیر `null` را چک
می‌کرد. برای داده پژوهشی، فیلدی که بیش از اندازه‌گیری واقعی ادعا کند از نبودش بدتر
است — پس نام به اندازه چیزی که کد آزمایش می‌کند باریک شد. تشخیص تغییر فشار کار مرحله
استخراج ویژگی است و مقادیر خام همه ذخیره شده‌اند.

### ۱۱. ذخیره خودکار: چرا Revision به تنهایی کافی نیست

AutoSave یک **Snapshot کامل** می‌نویسد نه Delta. اگر نوشتنِ قدیمی‌تر دیرتر تمام شود،
رکورد ذخیره‌شده عقب می‌رود و خطی که هیچ‌کس حذفش نکرده گم می‌شود. دو نگهبان لازم است:

۱. **صف به‌ازای هر جلسه** — دو نوشتن هم‌زمان در جریان نیستند.
۲. **نگهبان Revision** — نوشتنی که از قبل کهنه بوده اصلاً وارد صف نمی‌شود.

اما یک شمارنده Revision متعلق به **یک عمر ویرایشگر** است: با هر Mount از صفر شروع
می‌شود. مقایسه عددی از یک عمر با عددی از عمر دیگر بی‌معنی است — و در عمل فاجعه‌بار:

> AutoSave تا Revision ۱۰ می‌رسد → کامپوننت Remount می‌شود → همان جلسه بازیابی می‌شود →
> کاربر یک تغییر می‌دهد → این تغییر Revision ۱ از شمارنده جدید است → با ۱۰ مقایسه و
> **دور ریخته می‌شود**. AutoSave موفقیت گزارش می‌کند در حالی که چیزی ذخیره نمی‌شود.

**راه‌حل:** هر عمر ویرایشگر یک **Epoch** (توکن یکتا) می‌سازد که همراه هر نوشتن ارسال
می‌شود. Revisionها فقط **داخل یک Epoch یکسان** مقایسه می‌شوند. نوشتنی از Epoch متفاوت
همیشه پذیرفته می‌شود و علامت را بازنشانی می‌کند — چون قطعاً از عمر بعدی می‌آید (عمر قبلی
باید تمام می‌شد تا این یکی شروع شود). ترتیب بین دو Epoch را همان صف تضمین می‌کند.

نکته دوم: اگر نوشتنی **شکست بخورد**، ادعای Revision آزاد می‌شود. ادعا برای محافظت از
Snapshot‌ی است که واقعاً ذخیره شده؛ نگه‌داشتن آن پس از شکست، تلاش مجدد با همان Revision
منطقی را برای همیشه مسدود می‌کرد.

### ۱۲. چرا IndexedDB و نه localStorage؟

یک جلسه با چند هزار نقطه به‌راحتی از سهمیه ~۵ مگابایتی localStorage عبور می‌کند، و
نوشتن در آن **همگام** است و رشته اصلی مرورگر را حین رسم قفل می‌کند. localStorage در این
پروژه فقط برای سه مقدار کوچک (آخرین رنگ، ضخامت و ابزار) استفاده می‌شود.

## محدودیت‌های نسخه فعلی

این‌ها آگاهانه خارج از محدوده دو هفته اول بوده‌اند:

- **بازپخش انیمیشنی (Replay) و Timeline** پیاده‌سازی نشده است. زیرساخت داده‌ای آن کامل
  آماده است (هر نقطه زمان و ترتیب دارد)، اما رابط کاربری آن کار هفته‌های بعد است.
- **Clear در رابط کاربری قابل بازگشت نیست** (برای همین پیام تایید دارد) — اما در داده
  پژوهشی غیرمخرب است و خطوط پاک‌شده در فایل خروجی باقی می‌مانند.
- **هیچ Backend، دیتابیس سمت سرور، احراز هویت یا WebSocket** وجود ندارد؛ همه چیز محلی است.
- **دیتاست QuickDraw دانلود یا بسته‌بندی نشده است.** فقط نام دسته متناظر هر تکلیف ثبت
  می‌شود تا در آینده بتوان این ضبط‌ها را با آن دیتاست تطبیق داد.
- **نتایج آزمون در IndexedDB ذخیره نمی‌شوند.** ذخیره خودکار فقط جلسه نقاشی حالت «رسم
  آزاد» را پوشش می‌دهد؛ یک نتیجه آزمون تا زمانی که خروجی JSON گرفته نشود فقط در حافظه
  است. به همین دلیل هنگام رسم، هشدار ترک صفحه فعال می‌شود.
- **زمان پیشنهادی الزام‌آور نیست**: نمایش داده می‌شود، در فایل ثبت می‌شود و مقایسه
  می‌شود (`exceededRecommendedTime` و `overtimeMs`)، اما آزمون را به‌صورت خودکار پایان
  **نمی‌دهد**. این یک تصمیم آگاهانه است: قطع کردن ضبط در لحظه رسیدن به زمان، داده خام را
  ناقص می‌کند. نام میراثی فیلد همچنان `timeLimitSeconds` است.
- **`pointerType` سند سخت‌افزار نیست**: این مقدار همان چیزی است که Pointer Events مرورگر
  گزارش می‌کند. حالت شبیه‌سازی موبایل در Chrome ممکن است هنگام استفاده از موس واقعی
  `touch` گزارش کند، و ورودی لمسی شبیه‌سازی‌شده معمولاً هیچ داده فشاری ندارد. ArtiScan
  هیچ تشخیص مدل دستگاه یا fingerprinting انجام نمی‌دهد.
- **نقاط بیرون بوم نگه داشته می‌شوند، نه حذف**: Pointer Capture پس از خروج اشاره‌گر از
  بوم هم ضبط می‌کند. آن نقاط در داده خام می‌مانند و به‌جای حذف، در ویژگی‌ها به دو دسته
  «خام» و «داخل بوم» تفکیک می‌شوند.
- **«پوشش» مساحت کادر محیطی است، نه مساحت پیکسل‌های رنگ‌شده**: یک خط قطری از گوشه تا
  گوشه هم ۱۰۰٪ گزارش می‌کند.
- تست‌های خودکار روی منطق خالص و هوک‌ها هستند؛ تست رندر بوم به‌صورت **دستی** انجام
  می‌شود ([`docs/manual-test-checklist.md`](docs/manual-test-checklist.md) و
  [`docs/week-2-manual-test-checklist.md`](docs/week-2-manual-test-checklist.md)).
- در هر بار باز شدن برنامه یک رکورد جلسه در IndexedDB ساخته می‌شود؛ پاک‌سازی خودکار
  رکوردهای قدیمی هنوز اضافه نشده است.

## محدودیت‌ها و ملاحظات علمی

- **داده‌ها آزمایشی هستند.** در این مرحله هیچ داده واقعی از کودکان جمع‌آوری نشده و
  دسترسی به متخصص روان‌شناسی وجود نداشته است. تمام نقاشی‌های ثبت‌شده صرفاً برای آزمون
  فنی سامانه‌اند.
- **سامانه کاربرد تشخیصی روان‌شناختی ندارد.** ArtiScan هیچ تفسیر، امتیاز، برچسب یا
  نتیجه‌گیری روان‌شناختی تولید نمی‌کند و جایگزین متخصص نیست.
- نوآوری این پروژه در **ابزار ثبت داده و زیرساخت پژوهشی** است، نه در تشخیص.
- آماری که پنل نمایش می‌دهد (تعداد خطوط، تعداد نقاط، مدت جلسه) **شمارش عینی** است، نه
  تفسیر.
- **ویژگی‌های استخراج‌شده هفته دوم نیز صرفاً توصیفی‌اند.** طول مسیر، سرعت، پوشش بوم و
  تعداد مکث، اندازه‌گیری‌های هندسی و زمانی هستند. هیچ‌کدام امتیاز، برچسب یا معنایی
  ندارند و نباید به‌عنوان شاخص روان‌شناختی خوانده شوند.
- **آستانه مکث (۵۰۰ میلی‌ثانیه) یک انتخاب گزارش‌دهی است، نه یک یافته.** تعیین می‌کند
  کدام فاصله‌ها شمرده شوند و درباره علت هیچ‌کدام چیزی نمی‌گوید.
- نوع دستگاه ورودی (موس / لمس / قلم) عمداً در داده ثبت می‌شود، چون بر ویژگی‌های حرکتی
  اثر می‌گذارد و در هر تحلیل آینده باید در نظر گرفته شود. به همین دلیل سرعت بر حسب
  **واحد نرمال‌شده بر ثانیه** گزارش می‌شود تا مستقل از اندازه صفحه باشد.
